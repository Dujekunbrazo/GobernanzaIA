# PROMPT 96.3 - Compilador adversarial de handoffs M0 para motor activo F1

> [!IMPORTANT]
> Bootstrap obligatorio de gobernanza antes de usar este prompt:
> leer `AGENTS.md`, cargar Skills canonicas aplicables, usar
> `governance_search` para gobernanza con `phase`/`document_type` cuando
> aplique, usar `symdex_code` para codigo vivo y `codebase-memory-mcp` para
> wiring/impacto/legacy cuando toque codigo, y declarar cualquier degradacion
> antes de recurrir a lectura bruta.

Actua como `motor auditor` bajo la gobernanza canonica del repositorio
`<nombre_repo>`.

## 0. Tesis del prompt

96.3 no es un informe brillante ni una auditoria formal.

96.3 es un **compilador adversarial de handoffs M0**:

1. recibe un MD M0 ya trabajado con el usuario;
2. extrae sus claims, decisiones, hipotesis y fronteras;
3. los tensiona con agentes de miradas opuestas;
4. verifica contra repo, gobernanza, codigo vivo y memoria estructural;
5. decide `LISTO_PARA_CLAUDE_F1` o `BLOQUEADO`;
6. produce una transferencia de estado final para motor activo F1 y una llave de
   chat corta para arrancar un nuevo chat sin contexto previo.

El output final debe ser municion limpia para `F1`, no deliberacion residual.

## 1. Frontera con el flujo F1-F7

96.3 audita y compila el **input M0**.

- `M0`: conversacion, aterrizaje tecnico, handoff transitorio.
- `96.3`: tensiona el handoff M0 y produce input final para F1.
- `F1`: motor activo crea `plan.md`.
- `F2`: motor auditor audita formalmente `plan.md`.
- `F3`: implementacion.
- `F4`: motor auditor post-audita implementacion y evidencia.
- `F5`: validacion real cuando aplique.
- `F6/F7`: cierre y lecciones.

Reglas duras de frontera:

- 96.3 NO crea `plan.md`.
- 96.3 NO implementa codigo.
- 96.3 NO emite auditoria formal `F2`.
- 96.3 NO emite post-auditoria formal `F4`.
- 96.3 puede simular preguntas que F2/F4 harian, pero solo para endurecer el
  input M0.
- Si el input M0 ya contiene tramos definitivos, DoD operativo cerrado o
  comandos F3, 96.3 debe degradarlos a orientacion o marcarlos como scope creep.

Reglas:

- si el usuario proporciona una ruta local explicita a un `.md` existente, ese
  archivo es el input primario aunque no siga el prefijo canonico;
- si proporciona un nombre exacto dentro de `doc/_drafts/` y existe un
  unico match exacto, ese archivo es el input primario aunque existan otros
  drafts;
- si pega Markdown, ese bloque es el input primario y se traza como
  `procedencia=chat`;
- si la referencia es parcial o contextual y produce varios candidatos
  razonables, `Decision = BLOQUEADO` con `Causa = INPUT_M0_AMBIGUO`;

Path canonico preferente para inputs que proceden del prompt 97:


Si 96.3 produce un MD final y tiene permiso de escritura, debe escribir o

derivar `initiative_short_id` y escribir el MD final canonico, dejando trazado

## 4. Claim Ledger

El Claim Ledger es el centro de 96.3.

Antes de lanzar agentes, extrae del input M0 todas las afirmaciones materiales:

- decisiones cerradas;
- hipotesis abiertas;
- restricciones;
- no-alcance;
- claims sobre codigo vivo;
- claims sobre roadmap/canon;
- claims sobre F5/validacion real;
- claims sobre write set o rutas;
- claims sobre dependencias, precondiciones o commits.

Cada claim debe tener `claim_id` estable.

Estados finales permitidos:

- `conservar`: sobrevive sin cambio material;
- `corregir`: se mantiene la tesis, pero se afina o sustituye un detalle;
- `eliminar`: se retira por contradiccion material o scope creep;
- `abierto`: requiere resolucion antes de F1 o debe pasar como pregunta abierta
  con criterio de cierre;
- `bloqueante`: impide producir input F1 completo.

Reglas:

- decisiones marcadas `[CERRADA]` o equivalentes parten como `conservar`;
- reabrir una decision cerrada exige evidencia material, no opinion;
- `eliminar` es destructivo y exige doble validacion:
  1. un agente cita evidencia material verificable;
  2. el Integrador valida explicitamente que eliminar no deja la iniciativa sin
     canon de respaldo.
- si un agente propone `eliminar` y el Integrador no valida, el estado final
  baja a `abierto`;
- cada `corregir`, `eliminar`, `abierto` o `bloqueante` debe tener efecto
  explicito sobre F1.

Formato minimo de ledger:

```yaml
claim_id: CL-001
claim: "<afirmacion material>"
source: "<seccion/ruta/input/chat>"
default_status: conservar|abierto
agent_findings:
  - agent: "<agent_id>"
    proposed_status: conservar|corregir|eliminar|abierto|bloqueante
    evidence: "<repo|codigo|memoria|fuente externa|conversacion>"
    rationale: "<razon breve>"
integrator_validation:
  final_status: conservar|corregir|eliminar|abierto|bloqueante
  rationale: "<razon final>"
effect_on_f1: "<como debe aparecer o no aparecer en plan.md>"
```

## 5. Hipotesis abiertas para tension

Si el input M0 trae una seccion tipo `Hipotesis abiertas para tension`, no la
colapses ni la resuelvas por intuicion.

Cada hipotesis abierta debe:

- entrar al Claim Ledger;
- asignarse a uno o mas agentes;
- cerrarse como `conservar`, `corregir`, `abierto` o `bloqueante`;
- quedar con criterio de cierre verificable si sigue abierta.
