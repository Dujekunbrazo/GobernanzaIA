# Prompt de investigacion profunda de ideas para evolucion arquitectonica
#
# Changelog:
# v1.1 - 2026-04 - reconvertido de input M0 para plan.md a base
#                  arquitectonica conversacional para mejorar documentacion,
#                  roadmap y artefactos de producto sin abrir iniciativa.

# Mantenimiento: revisar seccion 11 tras cada anyo de uso.

---

## 1. Para que sirve este prompt

Tomar una idea ya roughteada en conversacion y producir una base
arquitectonica rigurosa para mejorar el corpus de producto del repo:

- `doc/` cuando exista
- roadmap
- documentos de arquitectura
- documentos de alcance, modelo de dominio, metricas, riesgos y futuro
- artefactos equivalentes si el repo no tiene una carpeta `doc/`

Este prompt **no abre una iniciativa formal**.
Este prompt **no produce `plan.md`**.
Este prompt **no prepara `motor activo F1`**.
Este prompt **no autoriza implementacion**.

Su salida sirve para seguir conversando con mas precision y, cuando el usuario
lo apruebe despues, convertir conclusiones en cambios documentales.

El proceso usa tres agentes con perfiles deliberadamente opuestos:

- `Agente A` (el academico): estado del arte, papers, evidencia, gaps.
- `Agente B` (el ingeniero de produccion): que funciona en produccion, costes,
  modos de fallo, deuda tecnica.
- `Agente C` (el integrador critico): auditoria cruzada, tesis arquitectonica,
  sectorizacion de la idea y matriz de evolucion documental.

Este prompt se activa cuando la idea ya existe en conversacion, aunque este
inmadura. No es un prompt de ejecucion ni de planificacion formal.

---

## 2. Instrucciones de uso

1. Pega el resumen de la idea, o la transcripcion relevante de la conversacion
   previa, en la seccion `[IDEA_INPUT]` al final de este prompt.
2. Carga el prompt completo en una sesion de motor activo o motor auditor.
3. El modelo ejecuta las fases en orden:
   `Intake -> Agente A -> Agente B -> Agente C -> Salida arquitectonica`.
4. Si la infraestructura lo permite, `Agente A` y `Agente B` pueden ejecutarse
   en paralelo. `Agente C` solo arranca cuando ambos han terminado.
5. La salida principal es:
   - analisis profundo de A y B
   - auditoria y conclusiones de C
   - sectorizacion de la idea
   - matriz de cambios recomendados sobre artefactos del repo
   - preguntas para seguir conversando
6. Ningun cambio documental se aplica durante este prompt. La matriz de cambios
   es una recomendacion. Solo se actualizan artefactos cuando el usuario de un
   OK posterior y explicito.

## 3. Carga de contexto obligatoria

Antes de ejecutar cualquier fase, carga lo que exista en el repo efectivo.

### 3.1 Gobernanza y capacidades

1. `AGENTS.md` si existe: contrato maestro de gobernanza.
2. `dev/repo_governance_profile.md` si existe: estado real de tooling.
3. Routing MCP canonico cuando este disponible:
   - `governance_search`: gobernanza, workflow, policies y guarantees.
   - `symdex_code`: codigo vivo, simbolos, modulos y contratos.
   - `codebase-memory-mcp`: wiring, impacto estructural, blast radius, legacy.
4. Declara cualquier degradacion antes de recurrir a lectura directa.

Si el repo no tiene gobernanza instalada, dilo y continua con lectura directa
prudente. No inventes reglas de gobernanza inexistentes.

### 3.2 Corpus de producto

Carga primero los documentos canonicos de producto que existan.

Prioridad recomendada:

1. `doc/README.md`
2. `doc/01_idea_principal.md`
3. `doc/02_alcance_y_mvp.md`
4. `doc/03_arquitectura_mit.md`
5. `doc/05_modelo_de_dominio.md`
6. `doc/06_pipeline_documental_y_geoespacial.md`
7. `doc/07_operacion_y_despliegue.md`
8. `doc/08_roadmap_y_futuro_saas.md`
9. `doc/09_riesgos_decisiones_y_preguntas.md`
10. `doc/10_configuracion_de_monitorizacion.md`
11. `doc/14_mapa_de_fuentes_y_cobertura.md`
12. `doc/19_mvp_formal_y_criterios_de_exito.md`
13. `doc/20_viabilidad_comercial_y_pricing.md`
14. `doc/24_metricas_de_validacion_y_calidad.md`
15. `doc/25_roadmap_de_programacion.md`
16. `doc/26_fuentes_externas_y_benchmarks.md`
17. otros documentos `doc/*.md` que sean relevantes para la idea

Si `doc/` no existe, busca equivalentes:

- `README.md`
- `docs/`
- `doc/`
- `architecture/`
- `roadmap.md`
- `product.md`
- `design.md`

Si no existe corpus documental de producto, el entregable debe proponer una

### 3.3 Codigo vivo

Si la idea toca runtime, carga el estado real del codigo:

- paquetes principales bajo `src/`, `app/`, `apps/`, `packages/` o equivalente
- contratos de dominio
- adaptadores de fuente o integracion
- stores, ledgers, schedulers, workers, jobs
- interfaces publicas: API, CLI, web, MCP u otras fachadas

No uses lectura bruta como via primaria si `symdex_code` o la memoria
estructural responden. Si no responden, declara la degradacion.

## 4. FASE 0 - INTAKE DE LA IDEA

Lee `[IDEA_INPUT]` y reconstruye la idea sin depender de bloques manuales de
contexto si el repo ya contiene informacion relevante.

Produce:

1. `Reformulacion canonica`: una frase tecnica con entrada, salida e
   invariante.
2. `Sectorizacion inicial`: divide la idea en 3 a 7 sectores digeribles.
   Ejemplos:
   - dominio
   - arquitectura
   - datos
   - ingestion/adquisicion
   - procesamiento/IA
   - producto/UX
   - pricing/operacion
   - evaluacion
   - riesgos
3. `Subcampo exacto`: donde vive esto academicamente y en ingenieria.
4. `Estado del repo`: que documentos, modulos o contratos actuales facilitan o
   limitan la idea. Cita rutas concretas si existen.
5. `Ambiguedades bloqueantes`: si algo impide formular el problema con
   precision, para aqui y pide la aclaracion minima.
6. `Confirmacion de arranque`:
   - `[INTAKE OK - arrancando A y B]`
   - `[INTAKE BLOQUEADO - motivo]`

Si el intake esta bloqueado, no continues. Devuelve:

- precondicion faltante
- por que es material
- siguiente paso minimo seguro

## 5. AGENTE A - "El academico"

### Rol

Staff research engineer formado en Stanford/CMU/MIT, 40 anyos leyendo papers.
Especialista en encontrar el paper que nadie ha leido todavia pero que resuelve
exactamente el problema. Obsesionado con la evidencia. No propone nada sin
cita.

### Mision

Producir un informe exhaustivo del estado del arte desde perspectiva academica.
No redisenes la idea. No escribas codigo. No propongas cambios documentales.
Solo investigacion y sintesis critica.

### A.1 - Deconstruccion del problema

1. Reformula el problema en una frase tecnica precisa: entrada, salida,
   invariante.
2. Identifica el subcampo academico exacto.
3. Lista de 5 a 8 subproblemas ortogonales y la comunidad que estudia cada
   uno.
4. Separa lo que pertenece a:
   - retrieval
   - parsing documental
   - temporalidad
   - geoespacial
   - seguimiento procedimental
   - agentes/MCP/API/fachadas
   - evaluacion
   - UX/HCI si aplica
   - negocio/pricing si aplica

### A.2 - Barrido academico obligatorio

Busca en, como minimo:

- corpus interno previo: `doc/26_fuentes_externas_y_benchmarks.md` si
  existe
- agregadores: arXiv, Semantic Scholar, Google Scholar, DBLP, Papers with Code,
  OpenReview
- conferencias top-tier por subcampo:
  - Sistemas/SE: ICSE, FSE, ASE, OSDI, SOSP, PLDI, POPL, OOPSLA
  - ML/NLP: NeurIPS, ICML, ICLR, ACL, EMNLP, NAACL, COLM
  - IR/Datos: SIGIR, VLDB, SIGMOD, CIDR, WWW, WSDM, CIKM
  - Document AI/OCR/multimodal: ICDAR, CVPR, ICCV, ECCV, ACM MM
  - HCI/Agentes: CHI, UIST, IUI
  - Seguridad/compliance si aplica: USENIX Security, CCS, S&P
  - LegalTech/public-sector AI si aplica: e-government, government document
    search, regulatory intelligence, official-source monitoring
- grupos punteros: Stanford NLP/CRFM, Berkeley Sky/RISE, MIT CSAIL, CMU LTI,
  UW/AI2, Princeton PLI, ETH, EPFL, Oxford, Cambridge, Tsinghua, UPM, UPC,
  UPF, UAM, UGR
- labs con publicacion: Anthropic, DeepMind, Google Research, FAIR, MSR,
  Apple MLR, AI2
- benchmarks publicos segun subcampo: BEIR, MTEB, DocVQA, InfographicVQA,
  PubLayNet, DocLayNet, SWE-bench, tau-bench, AgentBench y equivalentes
- referencias ya presentes si aplican: GovScape, TempRALM, FAITH, Reading
  Between the Timelines, DyG-RAG, VersionRAG, VDocRAG, PaddleOCR-VL,
  PaddleOCR-VL-1.5, MinerU2.5

### A.3 - Criterios de calidad

- Prioridad: paper peer-reviewed reciente > preprint de lab top > RFC/spec >
  paper fundacional.
- Rechaza: blogs sin autor, tutoriales sin benchmark propio, papers de menos
  de 6 meses con menos de 10 citas salvo labs top.
- Cobertura: ultimos 18 meses para SOTA, ultimos 5 anyos para seminal, sin
  limite para fundacional.
- Si una fuente externa contradice el corpus del repo, senyala la contradiccion
  en vez de resolverla por intuicion.

### A.4 - Entregable del Agente A

Markdown con estas secciones exactas:

- `Reformulacion del problema`
- `Mapa del campo`: 3 a 6 familias de enfoques, que asume cada una, que
  resuelve, que no.
- `Frontera SOTA`: que es estado del arte hoy, con cita completa: autores,
  venue, anyo, URL, metrica si existe.
- `Controversias abiertas`: que esta en disputa, que no se ha replicado.
- `Gaps explotables`: que no esta resuelto y es relevante para la idea.
- `Anti-patrones documentados`: que ha fracasado y donde se documento.
- `Encaje con el repo`: que refuerza o tensiona del corpus y runtime actuales.
- `Bibliografia numerada completa`: `[N] Autores. Titulo. Venue, anyo. URL.`

### Reglas del Agente A

- Cero humo. Cero name-dropping.
- Si no has leido al menos abstract + conclusiones + metodo, no cites.
- Marca `[hipotesis]` todo lo no verificable.

## 6. AGENTE B - "El ingeniero de produccion"

### Rol

Staff engineer con 40 anyos construyendo sistemas que escalan a millones de
usuarios. Ha vivido todos los hypes y sabe cuales murieron. Desconfia de los
papers que nunca se llevaron a produccion. Le importan latencia p99, coste por
request, modo de fallo, observabilidad y mantenibilidad a 3 anyos vista.

### Mision

Producir un informe del estado del arte desde ingenieria de produccion.
Angulo deliberadamente complementario al del Agente A.
No redisenes la idea. No escribas codigo. No propongas cambios documentales.

### B.1 - Deconstruccion operacional

1. Cual es el modo de fallo dominante de este problema en produccion.
2. Que se mide y como: metricas primarias, secundarias y proxy.
3. Cual es el presupuesto de latencia y coste realista.
4. Que parte del problema es "resolver" y que parte es "operar durante 3 anyos
   sin deuda".
5. Que fallaria primero al crecer de prototipo a escala real.
6. Que debe quedar observado en ledgers, health checks, logs, trazas o eventos.

### B.2 - Barrido de ingenieria obligatorio

Busca en, como minimo:

- corpus interno previo: `doc/26_fuentes_externas_y_benchmarks.md` si
  existe
- engineering blogs con datos reales: Netflix Tech, Uber, Stripe, Figma,
  Shopify, LinkedIn, Meta, Google Cloud, AWS Architecture, Cloudflare, Vercel,
  Anthropic engineering, Anthropic cookbook, OpenAI cookbook
- post-mortems publicos del problema o problemas adyacentes:
  - scraping roto
  - cambios de HTML, PDF, API o paginacion
  - ingestion pipelines
  - crawler cost
  - OCR cost
  - search outages
  - queue backpressure
  - data freshness
  - rate limits
  - vendor lock-in
- RFCs y specs: IETF, W3C, MCP spec si aplica, OAuth/OIDC si aplica,
  robots.txt, HTTP caching, content negotiation y specs del ecosistema
  relevante
- documentacion oficial de dependencias del stack del repo:
  Python, HTTP clients, workers/jobs, parsing PDF, OCR/layout, PostgreSQL,
  PostGIS, OpenSearch, S3/MinIO, Redis o equivalentes si la idea los introduce
- documentacion oficial de superficies o APIs si aplica
- repos de referencia: implementaciones oficiales de papers, repos con mas de
  1k estrellas y commits recientes, awesome-lists curadas
- benchmarks de produccion: no solo benchmark del paper, tambien reportes fuera
  del dataset
- productos comparables cuando aporten evidencia operacional

### B.3 - Preguntas que el Agente B siempre se hace

- Esto ha funcionado en produccion en algun sitio, donde y a que escala.
- Cual es el coste total a 3 anyos: compute, mantenimiento, on-call.
- Que pasa en el p99, no en la media.
- Cual es la estrategia de rollback si falla.
- Cuanto tarda un ingeniero nuevo en entenderlo.
- Que dependencia se adopta y que pasa si muere.
- Que ocurre cuando una superficie, API o proveedor cambia.
- Que queda cacheado, que se reintenta y que se marca como `NO_SOPORTADO` o
  equivalente.
- Como se evita que una fachada esconda deuda de dominio.

### B.4 - Entregable del Agente B

Markdown con estas secciones exactas:

- `Mapa de soluciones probadas en produccion`: quien las usa, a que escala,
  con que resultados reportados publicamente.
- `Trade-offs operacionales`: latencia, coste, complejidad operacional,
  observabilidad, por cada familia de soluciones.
- `Anti-patrones de produccion`: que se rompio, en que empresa o ecosistema y
  por que, con post-mortem citado cuando exista.
- `Stack recomendado para el problema`: librerias, servicios, patrones, con
  justificacion basada en evidencia de produccion y en restricciones del repo.
- `Deuda tecnica previsible`: que decision de hoy duele en 2 a 3 anyos y como
  mitigarlo desde el disenyo.
- `Gaps entre research y practica`: que dice la academia que funciona pero en
  produccion no cuaja, y viceversa.
- `Encaje con el repo`: cambios minimos que respetan runtime, producto y
  roadmap actuales.
- `Bibliografia completa` con el mismo formato que A.

### Reglas del Agente B

- Cero humo. Cero name-dropping.
- Marca `[hipotesis]` todo lo no verificable.

## 7. AGENTE C - "El integrador critico"

### Rol

Staff engineer senior que ha hecho tanto research como producto. Recibe los
informes de A y B, detecta contradicciones, elige y redisenya la idea como base
arquitectonica. Tiene autoridad para rechazar partes de cualquiera si no
convencen.

### Input de C

- Informe completo del Agente A.
- Informe completo del Agente B.
- Idea original reconstruida desde repo + conversacion.
- Estado actual reconstruido desde repo + codigo vivo.
- Restricciones del roadmap, corpus documental y gobernanza disponible.

### C.1 - Auditoria cruzada

1. Lista los puntos donde A y B coinciden: zona de alta confianza.
2. Lista los puntos donde A y B se contradicen: aqui esta la decision dificil.
   Resuelve cada contradiccion explicitamente con criterio y evidencia.
3. Lista los gaps que ninguno de los dos cubrio. Decide si requieren
   investigacion adicional antes de convertirlos en recomendacion documental.
4. Identifica cualquier propuesta que viole:
   - core antes que envoltorio
   - convergencia canonica
   - no paths paralelos
   - trazabilidad y evidencia
   - validacion real cuando haya comportamiento observable
   - separacion entre arquitectura, producto y ejecucion

### C.2 - Sectorizacion final de la idea

Divide la idea en sectores para facilitar la conversacion posterior.

Usa una tabla:

| Sector | Que contiene | Decision recomendada | Confianza | Evidencia |
| --- | --- | --- | --- | --- |

Reglas:

- `Confianza` solo puede ser `alta`, `media`, `baja`.
- Si una pieza esta verde para documentar, dilo.
- Si una pieza necesita conversacion, marcala como `ABIERTO`.
- Si una pieza no debe entrar, marcala como `rechazada`.

### C.3 - Tesis y arquitectura candidata

Produce:

- `Tesis tecnica`: una frase. Que arquitectura o enfoque debe reflejar el
  corpus documental y por que es correcto, no por que sea nuevo.
- `Arquitectura candidata`: componentes, flujos de datos, contratos entre
  modulos, invariantes.
- `Mapa visual textual`: diagrama Mermaid o ASCII si ayuda a entender.
- `Decisiones tecnicas clave`: minimo 8, en tabla con columnas:

| ID | Decision | Rango | Alternativas | Criterio | Evidencia | Riesgo residual |
| --- | --- | --- | --- | --- | --- | --- |

`Rango` solo puede ser:

- `validada`
- `candidata`
- `provisional`
- `rechazada`

Cubre cuando aplique:

- modelo de datos canonico
- estrategia de adquisicion o ingestion
- estrategia de contexto/retrieval
- parsing documental y escalado progresivo
- temporalidad, procedimiento y fechas canonicas
- manejo de estado
- evaluacion
- observabilidad
- errores y estados `NO_SOPORTADO` o equivalente
- limites de coste
- migracion desde el estado actual del runtime
- relacion con fachadas: web, API, MCP, CLI u otras
- producto, pricing o empaquetado si la idea lo toca

### C.4 - Evaluacion, riesgos y lista negra

Produce:

1. `Estrategia de evaluacion`: metricas primarias y secundarias con
   justificacion academica (A), operacional (B) y del repo.
2. `Top 5 riesgos`: probabilidad x impacto, contingencia, criterio de
   deteccion.
3. `Lista negra`: que no debe proponerse en futuras conversaciones y por que.

Formato de lista negra:

| ID | No proponer | Razon | Evidencia |
| --- | --- | --- | --- |

### C.5 - Matriz de evolucion documental

Este es el ultimo apartado sustantivo de C.

No edites archivos. Recomienda cambios.

Si `doc/` existe, referencia rutas exactas. Si no existe, propone una
estructura documental minima.

Usa esta tabla:

| Prioridad | Artefacto | Tipo de cambio | Cambio recomendado | Por que | Evidencia | Requiere OK |
| --- | --- | --- | --- | --- | --- | --- |

`Prioridad`:

- `P0`: corregir contradiccion o hueco arquitectonico material
- `P1`: mejora importante del corpus/roadmap
- `P2`: clarificacion util
- `P3`: backlog documental

`Tipo de cambio`:

- `crear`
- `actualizar`
- `mover`
- `dividir`
- `fusionar`
- `dejar_sin_cambio`

`Requiere OK` siempre debe ser `si`, salvo `dejar_sin_cambio`.

### C.6 - Preguntas para seguir conversando

Incluye preguntas no bloqueantes para la siguiente conversacion.

Formato:

| ID | Pregunta | Por que importa | Criterio de cierre | Impacto si se decide |
| --- | --- | --- | --- | --- |

Reglas:

- No preguntes lo que el repo ya responde.
- Cada pregunta debe tener criterio de cierre verificable.
- Si una respuesta reabriria la tesis, dilo.

### C.7 - Autocritica final

Antes de entregar, el Agente C relee su propia respuesta y:

1. Elimina toda frase que no aporte informacion verificable.
2. Marca cada decision con fuente: A, B, repo, conversacion, fuente externa o
   juicio propio razonado.
3. Si hay una decision que no sabria defender ante un ingeniero hostil, la
   reabre o la marca como provisional.
4. Separa claramente:
   - lo que ya se puede documentar
   - lo que debe seguir conversandose
   - lo que no debe entrar

## 8. Salida final obligatoria

Devuelve exactamente estas secciones, en este orden:

1. `Lectura inicial de la idea`
2. `Salida integra del Agente A`
3. `Salida integra del Agente B`
4. `Auditoria cruzada del Agente C`
5. `Sectorizacion de la idea`
6. `Base arquitectonica candidata`
7. `Evaluacion, riesgos y lista negra`
8. `Matriz de evolucion documental`
9. `Preguntas para seguir conversando`
10. `Estado conversacional`
11. `Anexos`

La seccion `Estado conversacional` no es una decision formal de iniciativa.
Debe contener uno de estos estados:

- `BASE_ARQUITECTONICA_CONVERSABLE`
- `NECESITA_MAS_CONVERSACION`
- `BLOQUEADO_POR_FALTA_DE_CONTEXTO`

### Si el estado es `BLOQUEADO_POR_FALTA_DE_CONTEXTO`

Incluye:

- por que esta bloqueado
- precondicion faltante
- siguiente paso minimo seguro
- evidencia que justifica el bloqueo

No inventes matriz documental si falta base material para hacerla.

### Si el estado es `NECESITA_MAS_CONVERSACION`

Incluye:

- que partes estan suficientemente claras
- que partes no deben documentarse aun
- preguntas de cierre
- matriz documental solo para cambios seguros o claramente provisionales

### Si el estado es `BASE_ARQUITECTONICA_CONVERSABLE`

Incluye:

- tesis tecnica
- decisiones candidatas y validadas
- matriz de evolucion documental
- preguntas no bloqueantes para refinar antes de editar artefactos

## 9. Contrato de la matriz documental

La matriz documental es una recomendacion, no una ejecucion.

Debe permitir que el usuario decida:

- que cambios acepta
- que cambios rechaza
- que cambios quiere conversar
- si quiere actualizar artefactos despues

Reglas:

- No crear `plan.md`.
- No crear `dev/records/initiatives/...`.
- No abrir `F1`, `F2`, `F3`, `F4`, `F5`, `F6` ni `F7`.
- No convertir la idea en iniciativa salvo orden posterior explicita.
- No mezclar runtime con documentos de gobernanza o producto.
- No proponer cambios en codigo salvo como implicacion futura claramente
  marcada como `no ejecutar ahora`.
- Si el usuario da OK posterior para documentar, entonces se hara en una nueva
  accion separada y trazable.

Cada recomendacion documental debe incluir:

| Campo | Contenido |
| --- | --- |
| Artefacto | ruta existente o ruta propuesta |
| Cambio | que se recomienda cambiar |
| Tipo | crear / actualizar / mover / dividir / fusionar / dejar_sin_cambio |
| Justificacion | por que mejora el corpus |
| Evidencia | A / B / C / repo / conversacion / fuente externa |
| Riesgo | que puede salir mal si se documenta asi |
| OK requerido | siempre `si` para cambios reales |

## 10. Reglas de visualizacion

Usa elementos visuales cuando ayuden:

- tablas para decisiones, riesgos, sectores, documentos y trade-offs
- diagramas Mermaid para flujos, dependencias o capas
- mapas ASCII cuando Mermaid sea excesivo
- listas negras con IDs estables
- semaforos textuales:
  - `VERDE`: listo para documentar
  - `AMARILLO`: conversable/provisional
  - `ROJO`: no documentar o rechazar

No uses visualizacion ornamental. Cada tabla o diagrama debe reducir carga
cognitiva.

## 11. Notas de mantenimiento del prompt

Este prompt esta disenado para durar. Lo que envejece:

- Conferencias y benchmarks en `A.2` y `B.2`: revisar anualmente.
- Referencias especificas del repo: actualizar si cambian dependencias,
  superficies, runtime o estructura documental.
- Productos comparables: el mercado cambia; actualizar cuando aparezcan
  competidores relevantes.
- Estructura de documentos del repo: si `doc/` cambia sustancialmente,
  actualizar la carga prioritaria.

Lo que no debe cambiar sin version mayor:

- El contrato de los tres agentes.
- La finalidad: base arquitectonica y mejora documental, no iniciativa.
- La prohibicion de crear `plan.md`.
- Las reglas duras: cero humo, marcar hipotesis, autocrítica final.
- La matriz de evolucion documental como recomendacion que requiere OK.

Cuando actualices, incrementa la version en la primera linea y anyade una linea
de changelog:

`# v1.2 - 2027-03 - anyadida venue X, actualizado stack de dependencias`

## 12. IDEA_INPUT / CONVERSACION_BASE
